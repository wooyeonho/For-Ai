# RUN-009 — G4 scheduler daemon (unattended ticking under repeated kills, still not gate acceptance)

- Gate worked on: **G4 Workflow Runtime**, daemon half — stays `PENDING`. Every machine check passes and the release
  train still refuses the promotion: `gate pass --gate G4` → `promoted: false … earlier gates not passed:
  G2=PENDING, G3=PENDING`.
- Blocked by: **G2** (`PENDING` / `NEEDS_SOURCE`, no official chat export) and therefore **G3**.
- Authority: A2 (local, reversible). Network: NONE. Cost: 0 KRW. No provider call.
- RUN-008 left this honest gap: *"ticks are explicit invocations; no long-running daemon exists, and reboot-level
  evidence has not been collected."* This RUN closes the daemon half of it. A true OS reboot is still not evidenced —
  see §Limitations.

## The invariant this RUN exists to prove

> a scheduler that runs unattended, is killed at arbitrary moments, and is restarted over and over still serves
> each boundary exactly once — and still makes progress

This is a property of a whole soak, not of one tick: RUN-008 proved a single tick cannot double-serve one boundary at
the two dangerous instants. Here a long-running process serves a schedule that keeps coming due, dies mid-flight at
moments nobody chose, and a brand new process takes over each time as if the machine had restarted.

## What was built

1. `migrations/0014_scheduler_daemon.sql` (additive; no existing table touched) — `daemon_soak_cycles`
   (`death` in `sigkill`/`clean`, `killed`, `ran_ms`, `boundaries_served`, `duplicate_boundaries`, `duplicate_jobs`,
   `fires_regressed`, `ok`, detail) with append-only and no-delete triggers, and an honest-verdict trigger: a cycle may
   only be recorded as a pass if it really died the way it claims, no boundary was served twice, no job served two
   boundaries, and the served count never went backwards.
2. `src/domain/scheduler.mjs` — `runSchedulerDaemon(db, { tickMs, maxTicks, onOutcome, shouldStop, sleep }, clock)`.
   The loop arms nothing and releases nothing: every tick goes through `tickScheduler`, so the Owner's two switches
   plus the emergency stop remain the only thing that lets it act. `sleep` and `shouldStop` are injected, so the loop
   is testable without real time and stoppable without a signal.
3. `scripts/scheduler-daemon.mjs` — the real long-running process. `SIGTERM`/`SIGINT` end it cleanly between ticks;
   one line of stdout per fire and per refusal, so a supervisor can see how far a process got before it died.
4. `scripts/daemon-soak.mjs` — the restart soak. One armed schedule with a one-second interval; each cycle spawns a
   real daemon, lets it live a randomised 1–2 boundary windows, then `SIGKILL`s it (the final cycle ends it cleanly
   with `SIGTERM`, so a graceful shutdown is on the record next to the violent ones) and recomputes duplicates from
   raw rows. A soak where nothing ever fired would satisfy every duplicate check while proving nothing, so
   `served < cycles` is itself a failure (`DAEMON_SOAK_NO_PROGRESS`).
5. `scripts/independent-validation.mjs` — new `scheduler_daemon_recomputed` check from raw `daemon_soak_cycles` rows:
   dishonest passing cycles, and whether any soak on record is clean *and* has real kills *and* made progress.
6. `scripts/assert-seeded-defect-detected.mjs` — 2 new seeded defects (19 total): a soak cycle claiming a kill that
   never happened, and one calling a duplicated boundary a pass. Both are seeded by dropping the honest-verdict trigger
   in a throwaway database, so the check proves the *validator* catches the lie rather than only the trigger.
7. `scripts/local-ci.mjs` — `scheduler_daemon_restart_soak` is now a CI step (17 steps). The scheduler crash soak step
   now runs with `--no-record`: repeated CI runs no longer add rows to the kernel's soak evidence, so the recorded
   soaks are exactly the deliberate ones a RUN's evidence cites.
8. `test/daemon.test.mjs` — 5 tests: a daemon on a fresh install ticks forever and produces nothing
   (`EMERGENCY_STOP` every tick, 0 fires, 0 jobs); with the stop released it still refuses while the master switch is
   off; it serves each boundary exactly once as a driven clock advances; `shouldStop` ends the loop between ticks;
   and the evidence table refuses four flavours of flattering lie while accepting an honest failing row.

## Limitations recorded honestly

- **No OS reboot evidence.** Every death here is a process death. A real Windows/WSL restart with the daemon coming
  back under a supervisor (autostart, service registration) is G10 work and is not claimed.
- **No supervisor.** Nothing restarts the daemon automatically yet; the soak plays that role. There is no service
  unit, no autostart, no crash-loop backoff.
- **The daemon has no work to do in production.** Nothing in the kernel is armed: the master switch is `enabled = 0`,
  the emergency stop is `ON`, and the only schedule on the ledger is disarmed. The daemon is proven inert on a fresh
  install by test, not merely by intention.
- **Soak scale.** 8 cycles, ~13 seconds, 12 boundaries. Enough to break at-most-once if it were breakable per kill,
  not a 72-hour endurance claim (G11).
- **`npm run lint` / `npm run typecheck` do not exist** in this repository (`npm error Missing script`). Reported as
  absent, not as passing.
- **G4 is still `PENDING`.** Implementation and evidence are not gate acceptance; G2's missing official export is the
  only thing that can unblock the G3/G4 promotions.
