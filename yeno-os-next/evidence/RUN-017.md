## 1. What changed and why

RUN-015 fixed what the shell may draw; RUN-016 drew it. This RUN fixes **when** it redraws, which is
where a desktop UI usually starts lying: a screen refreshed on a timer is silently out of date
between ticks, and a screen patched from a stream that dropped events is assembled from state nobody
observed. `src/ui/follower.mjs` is the follower half of the shell, and the interesting part is not
parsing SSE — it is the policy for when the stream misbehaves.

| Rule | Why it is not optional |
|---|---|
| Sequence numbers only move forward; a repeat or a regression is dropped, never applied | applying an event twice double-counts it into the screen |
| A gap between the last seen sequence and the next forces a **refetch of the panels**, not a patch | a patched panel would show state assembled from events nobody saw |
| A dropped connection marks the screen `stale` and keeps the last known truth on it | clearing it destroys what the Owner was reading; pretending it is live is the actual failure |
| Reconnecting asks for `?from=<lastSeq>`, and reopening refetches before believing the screen | resume is a ledger position, not a server-side session, so it is exactly as trustworthy as the ledger's ordering |
| A frame split across TCP chunks is applied once, when complete; the `: open` comment moves no cursor | half a frame is not an event |

## 2. The loop, end to end, with no shell

`scripts/ui-follow-exercise.mjs` plays the part of the desktop app against a throwaway kernel and a
real `api serve` child process, talking only over the socket: follow `/events/stream`, redraw from
`/contract` + `/panels`, and assert what a real UI must get right.

```text
ui follow checks: 11, failed: 0
OK fresh_kernel_draws_every_button_disabled — 3 buttons
OK command_accepted_after_owner_released_the_stop — status 202
OK command_event_reached_the_follower — cursor 3
OK no_gap_forced_a_refetch_on_a_clean_stream
OK screen_shows_the_effect_only_after_its_event — cursor 3 visible in the timeline
OK released_stop_makes_the_buttons_pressable_again
OK dropped_connection_marks_the_screen_stale — stale: DISCONNECTED; last seen event 3
OK reopening_refetches_before_believing_the_screen
OK resume_delivers_only_events_after_the_last_seen_sequence — from 3 to 4
OK negative_control_gap_detection_removed — the check breaks with the rule removed
OK negative_control_replay_guard_removed — the check breaks with the rule removed
UI_FOLLOW_EXERCISE_PASS
```

The two negative controls are the reason the other nine mean anything: each copies
`src/ui/follower.mjs` into a temporary directory, deletes exactly one rule in the copy, imports the
copy and asserts the matching check then fails. Production sources are never patched and the copy is
removed. Without the gap rule a follower jumping 10 → 13 reports no refetch; without the replay rule
an already-seen sequence 5 is applied again.

The stop is released **only** inside the throwaway kernel, with an Owner reason on the record, and
the kernel is deleted at the end of the run. `state/yeno.db` is untouched and still stopped.
