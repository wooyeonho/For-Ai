## 1. What changed and why

RUN-015 fixed what the shell may draw, RUN-016 drew it, RUN-017 fixed when it redraws. The claim
those three imply is the one that matters to the Owner: **the screen can never disagree with the
ledger.** That is testable without pixels by drawing the same screen twice through paths that share
no step except the ledger itself, and comparing bytes.

```text
warm path  follower watched every event on /events/stream, then redrew from
           /contract + /panels over the socket (HTTP, read-only handle)
cold path  a separate process that never saw the stream opens the database
           read-only and renders (mc render)
                                   |
                        must be byte-identical
```

`scripts/ui-screen-soak.mjs` runs this as a bounded soak on a throwaway kernel. Each cycle
reconnects the follower from the previous head (a shell waking from sleep, a network blip, a
restarted facade), accepts one command, is refused twice, drains the stream to the head, then
compares the two screens.

Two refusals per cycle, on purpose: granting an approval is not in the vocabulary at all, and
promoting an inbox item that does not exist is refused by the domain. A refusal is where a UI is most
tempted to show its own optimistic guess, so the comparison happens immediately after one.

## 2. Result

```text
cycle 1: head 3, cursor 3, accepted 202, denied 400/422, identical true (44 lines)
cycle 2: head 5, cursor 5, accepted 202, denied 400/422, identical true (46 lines)
cycle 3: head 7, cursor 7, accepted 202, denied 400/422, identical true (46 lines)
cycle 4: head 9, cursor 9, accepted 202, denied 400/422, identical true (46 lines)
cycle 5: head 11, cursor 11, accepted 202, denied 400/422, identical true (46 lines)
cycle 6: head 13, cursor 13, accepted 202, denied 400/422, identical true (46 lines)
screen soak cycles: 6, divergent screens: 0, bad accepts: 0, leaked denials: 0, stale cursors: 0
UI_SCREEN_SOAK_PASS 6/6
```

Four assertions, each able to fail: no cycle may produce divergent screens, every accepted command
must answer `202`, **no** refused command may answer below `400`, and the follower's cursor may not
lag the ledger head. The stop is released on the throwaway kernel only, with an Owner reason on the
record, and the kernel is deleted at the end of the run; `state/yeno.db` is untouched and still
stopped.

The comparison is not a tautology. The warm screen's disabled-button state is derived from the
`emergency_stop_engaged` column the facade served, while the cold screen's comes from
`stopEngaged()` read straight from the database — so a facade that reported a stale or flattering
stop state would show up as a byte difference in the buttons.

- It proves the two read paths agree. It does not prove the future Tauri UI uses either of them; that
  check ships with the UI.
